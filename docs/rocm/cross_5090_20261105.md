## 已落实：FP32 累加的矩阵 HGEMV

`load("hgemv").hgemv_tensor_core_cute(a, b, out)` 现在有原生 AMD 实现。
输入和输出仍为 FP16，WMMA 使用 FP32 累加；名称对应原接口，内部累加精度明确不同。
原 FP16 WMMA 研究实现仍保留在 `kernels/rocm/hgemv_layouts.cu` 中，不被静默覆盖。

- 与 CUDA 共用的 15 个输入全部通过 `atol=rtol=0.003`；没有要求模仿 CUDA 的低精度误差。
- 对照研究还测试“每 K16 tile 舍入为 FP16”：精度只有 11/15，通过情况没有优于原 CUDA，
  因而默认接口采用完整 K 范围保持 FP32 状态的方案。
- 两张 AMD 卡分别 **66、63 项**检查通过：空维度、尾块、K=65536、正负抵消、
  动态范围、非法输入、两个并发 stream，以及输入设备与调用设备不同时的恢复。
- 反汇编确认 `v_wmma_f32_16x16x16_f16`；完整 ROCm 回归为 **23 模块、157 接口、890 项**。

| M × K | 新 HGEMV / ms | 同机 torch.mm / ms | 现状 |
| --- | ---: | ---: | --- |
| 64 × 128 | 0.008342 | 0.012054 | 此小规模更快，调度成本占比高 |
| 1024 × 1024 | 0.045405 | 0.013350 | 约慢 3.40 倍 |
| 4096 × 8192 | 0.311264 | 0.078172 | 约慢 3.98 倍，仍需优化 |

正确性和可运行性已解决；尚未解决大规模性能差距。
后续可针对 GEMV 的单列输出减少矩阵计算浪费，并探索分 K 和加载并行度。

## 剩余 56 个接口也完成 CUDA 基线试验

这 56 个接口的 41 个编译组全部成功编译，168 个函数用例全部实际运行。
其中 **53 个接口的全部用例通过**，总计 **162/168 个数值检查通过**。
剩余 3 个为 `hgemm_async.cu` 的 FP16 自身累加算法：每个接口在 K=256、512 时
超过原定 `atol=rtol=0.01`，K=128 通过。它们在 AMD 上还需要同时解决异步流水线替换
与精度策略，不能因有 CUDA 基线而升级为“ROCm 已支持”。

29 个 FlashAttention、20 个 HGEMM WMMA/MMA/CuTe、两个 TF32 WMMA SGEMM、
一个 warp-specialized HGEMM 和一个 cuBLAS TF32，共 53 个接口，通过本轮选定用例。

各接口的 shape、stage、布局与性能样本见 [56 接口报告](cross_5090_20261105/pending56_cuda.json)。

初次测试中三个 `...swizzle_qkv` Attention 失败，原因是测试器传入了普通 V。
原项目明确为这三个接口传入 `[B,H,D,N]` 的转置 V；修正测试器后 9/9 用例通过，
**没有因此修改原算子，也没有将测试器错误归咎于原项目**。其余同后缀接口仍按原调用约定
传入普通 V，不能只按名字统一转置。

与已支持组、精度研究组合后，**229/229 个原始计算接口都有 5090 运行证据**。
逐项选择原版或已说明的共享修复版，当前 **210 个接口的全部选定用例通过，19 个至少有一个
精度失败**（16 个原有精度保留项 + 3 个异步 HGEMM）。这不是“原版 210 个全部正确”或
“整个项目验收通过”；清单的 `cuda_comparison.source_kind` 和 evidence 明确区分源码版本。
ROCm 统计仍为 **157/229**，未用 CUDA 成功数替代迁移数。

## 独立 C++ benchmark：完成 CUDA 运行审计，整体验收仍不通过

原 benchmark 在 CUDA 13.4.92 / sm_120a 下编译。13.4 编译 FP4 CuTe 时，原值级
`static_assert(size<0>(...) == ...)` 触发 NVCC 常量解释器内部错误；改为读取同一
静态维度类型的 `::value` 后全套 10 个编译单元成功。**保留了断言条件，没有删除约束**。
编译器二进制与运行库分别留有 hash，见 [C++ 环境锁](../../scripts/cuda/cpp.environment.lock.json)。
修改只作用于 CUDA 分支；AMD FP4 重新运行 **1540 项检查全部通过**，见
[补充回归](fp4_cuda_assert_regression_20261105.json)。2026-11-03 的报告保留原源码指纹，
不被此次 CUDA 兼容修正覆盖。

| C++ 运行分组 | 5090 结果 | AMD 验收现状 |
| --- | --- | --- |
| 基础 256³ 入口、FP8、FP4 | 成功结束并输出误差 | FP8/FP4 有独立 AMD 路径；原多模块入口尚未迁移 |
| FA3 TMA copy、FA3 CuTe、FA2 CuTe、FA2 cp.async | 均成功结束 | 原 NVIDIA 调度仍待重写 |
| persist-D、split-D non-WS（含大 head、GQA/causal/tail 用例） | 均成功结束 | 尚无完整 AMD 等价实现；独立基础 FA 前向不替代这部分 |
| 512³ GEMM、B=1/H=2/N=256/D=64 Attention 性能 | 完成 3 warmup、10 repeat 的原脚本基线 | 跨平台同输入 C++ 性能验收尚未建立 |
| Hopper WGMMA | sm_120a 构建不包含此分支 | 5090 不具备 sm_90a 原样验证条件；AMD 必须替换机制 |

总计 **10 个运行分组全部正常退出**。原 benchmark 仅打印误差、不会因数值不合格返回
非零；FP4 的约 0.144～0.145 relFro 还包含量化前 FP64 参考与 NVFP4 的量化差异。
因此不能把退出码 0 当作完整数值资格，更不能把它与 AMD 的量化后参考混为同一门限。
本报告有意将 `qualification_passed` 保持为 false。

证据：[C++ 执行及库指纹](cross_5090_20261105/cpp_cuda.json)、
[编译失败、修复构建、完整 stdout](cross_5090_20261105/cpp_logs.json)。

**全仓验收结论：未通过。** 除原始接口的 72 个缺口，还剩 C++ 整体入口、FFPA、
CuTe/CuTe DSL 的 4 个 GPU 示例、swizzle 的 3 个独立 GPU 示例、Nsight 的 2 个 GPU 示例
和工具替代流程，以及未绑定的 WGMMA 等实验源码。后述小示例本轮仅审阅源码，
没有冒充已经完成 GPU 运行验收。数值实现可替换，NVIDIA 编译器 DSL 和分析工具本身
不能靠 HIP 名称替换变成 AMD 后端；需要独立示例和明确的工具映射。

| 异步 HGEMM | 3 | 原 `cp.async` 不能直接映射为 gfx1201 同一指令 | 复用已验证的 VGPR 预取、显式 load wait 和双 LDS 设计，检查 buffer 奇偶、实际重叠与 spill |
| cuBLAS TF32 | 1 | hipBLAS 在当前卡上拒绝该数学模式 | 明确的软件 TF32 路径或独立注明精度提升的 FP32 路径；不能仅做未标识的 FP32 别名 |
| FP16/BF16 原低精度算法 | 16 | CUDA 对照已证明多数为原算法的舍入限制 | 保留原精度模型及 CUDA 对照；逐个提供明确命名/标注的高精度实现再验收，不放宽现有门限 |
| **合计** | **72** | **56 待实现 + 16 精度保留** | **每项通过后才更新清单** |

尚无实验依据把这 72 个判为“数学运算无法在 AMD 上完成”。不能原样复用的是部分
NVIDIA 指令和执行机制；替代算法、数值精度、性能及完整 API 范围都需要继续验证。
229 的分母不涵盖独立 C++ 全套 benchmark、FFPA 和全部 Triton 示例，不能漏掉这些整体迁移工作。
