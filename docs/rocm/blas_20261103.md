# 原始 BLAS 接口迁移：2026-11-03

新增 3 个原始计算接口，累计 **153/229（66.81%）**。
实现：`kernels/rocm/blas_backend.cu`，调用 hipBLAS/rocBLAS。

| 原始入口 | ROCm 入口 | 数学模式与布局 |
| --- | --- | --- |
| sgemm_cublas | `load("sgemm").sgemm_cublas(a,b,c)` | FP32，COMPUTE_32F，A/B/C 行主序 |
| hgemm_cublas_tensor_op_nn | `load("hgemm").hgemm_cublas_tensor_op_nn(a,b,c)` | FP16 输入输出，COMPUTE_16F，A/B/C 行主序 |
| hgemm_cublas_tensor_op_tn | `load("hgemm").hgemm_cublas_tensor_op_tn(a,b,c)` | FP16，COMPUTE_16F，B 的物理存储为 `[N,K]` |

TN 保留原接口约定：形状仍为 `b[K,N]`，但元素按转置后的 `[N,K]` 顺序打包。
给定正常行主序 `b`，调用前使用 `packed_b = b.T.contiguous().view(K,N)`；
结果为原正常 `a @ b`。NN 路径直接传原正常 `b`。

原 `CUBLAS_COMPUTE_16F` 允许计算与中间存储采用至少 FP16 精度，不要求每个加法步骤
都向 FP16 舍入，见 [NVIDIA 计算类型定义](https://docs.nvidia.com/cuda/archive/12.4.0/cublas/index.html#cublascomputetype-t)。
本机 hipBLAS 对应枚举也明确为至少 16 位。本迁移保留该模式，不能将它当作前批 11 个
自定义 FP16 FMA kernel 的逐步算术模拟。严格 `16F_PEDANTIC` 不作为这些原接口的要求。

所有输入须同 GPU、匹配 dtype、连续二维，输出不能与输入共享 storage；拒绝梯度输入。
支持矩形、非对齐 tile 尺寸、零 M/N 和零 K（K=0 时清零输出）。
内部 device guard 恢复调用方设备，句柄按线程和设备缓存，随调用绑定当前 stream。
HGEMM 仍提供 `init_cublas_handle()`、`destroy_cublas_handle()` 管理当前线程／设备的
hipBLAS 句柄；二者不计入 229 个计算接口。已验证销毁后重新创建和计算。

## 验证

- [完整回归](qualification_20261103_blas.json)：物理 GPU0，23 模块、153 接口、837 项通过。
- [第二张卡](blas_device1_20261103.json)：物理 GPU1／逻辑 GPU1，SGEMM/HGEMM 13 接口、217 项通过。
- [BLAS 专项](blas_20261103.json)：170 项扩展检查、9 组性能比较。包含 3 个随机种子、
  FP64 参考、默认／非默认 stream、矩形及 K=1025、空输入、错误契约与句柄生命周期。
- [后端能力探测](blas_research_20261103.json)：32F 与普通 16F 共 12 项成功且精度通过；
  `16F_PEDANTIC` 与 `32F_FAST_TF32` 共 12 项返回状态 7（NOT_SUPPORTED），
  TF32 math mode 设置也返回 7。`sgemm_cublas_tf32` 仍未发布。

性能使用 HIP graph，5 轮交替 40ms 采样的中位数，基线为预分配输出的 `torch.mm`。
TN 的 B 打包在计时外；不代表包含预处理的端到端收益。

| 2048³ | 本接口 µs | PyTorch µs | 基线／本接口 |
| --- | ---: | ---: | ---: |
| FP32 | 1165.60 | 1167.66 | 1.002× |
| FP16 NN | 160.03 | 160.31 | 1.002× |
| FP16 TN | 135.97 | 160.91 | 1.183× |

完整报告还保留 256³、1024³；小形状存在略慢于基线的情况。
这些接口是原库调用路径的后端迁移，不计为新的自定义 WMMA kernel。
